VG Select: 3A — Deployment Guide

For the engineer who deploys and operates VG Select: 3A (Automated Agentic Architecture) as an internal service. People who use the deployed application should read the User guide; engineers integrating with the API or CLI should read the Consumer guide. Version 0.4.0.

1. What you are deploying

A single, stateless Python web application (FastAPI on Uvicorn) that:

  • serves the web UI at / and the user guide at /guide;
  • exposes a REST API under /api/v1/ with an OpenAPI document at /openapi.json, Swagger UI at /docs and ReDoc at /redoc;
  • scans uploaded or mounted repositories, ranks agent topologies, staffs each role from the model catalog, grades existing agents from traces, and renders the architecture PDF and the LangGraph skeleton.
PathPurpose
/, /guideWeb UI (three-step flow, tooltips, report card, downloads) and the built-in user guide
/api/v1/recommendRank topologies for a workload profile; returns the plan, model per role, report card (when traces are supplied) and a Markdown report
/api/v1/scan, /api/v1/scan/uploadScan a repository (server path, git URL, or uploaded zip; optional traces) and infer the profile, then recommend
/api/v1/report-cardAgent report card from a profile, optional scan object and run-time traces
/api/v1/recommend/pdf, /api/v1/recommend/skeletonArchitecture document (PDF) and downloadable LangGraph project skeleton (zip)
/api/v1/catalog, /api/v1/catalog/validateThe model ecosystem catalog and a validator for new entries
/api/v1/describeOptional: infer the profile from prose with Claude (needs the llm extra and Anthropic credentials)
/api/v1/fields, /api/v1/examples, /api/v1/topologies, /api/v1/citationsReference data
/healthLiveness/readiness plus the effective configuration (scan roots, catalog, feature flags)

There is no database and no persistent state. Uploaded archives, cloned repositories and traces are processed in memory or a temporary directory and deleted when the request finishes. The only configuration artefact is the model catalog JSON.

All computation is CPU-bound Python. A single replica handles interactive use for a team; add replicas for concurrency, not for memory.

3. Prerequisites and sizing

ItemRequirement
RuntimePython 3.11 or newer (3.12 recommended), or Docker. No compiled extensions beyond what pip wheels provide.
Python packagesInstalled by the service extra: FastAPI, Uvicorn, Pydantic, python-multipart, reportlab. The llm extra adds the Anthropic SDK for the optional describe endpoint.
GitOnly if you enable scanning by git URL (VGSELECT_ALLOW_GIT_CLONE=1).
NetworkInbound from your users to the proxy. Outbound is not required, except to git remotes (if cloning is enabled) and to api.anthropic.com (if describe is enabled). The UI has no external front-end dependencies.
CPU / memoryBaseline ~120 MB RSS per replica. A recommendation takes milliseconds; a PDF 0.1-0.5 s; a scan 0.1-10 s of CPU depending on repository size (cap: 20,000 files, 1 MB each); a report card is linear in trace steps. Start with 0.25-1 vCPU and 512 MB per replica; give scan-heavy deployments 2 vCPU.
DiskTemporary space for uploads and clones: reserve at least 2× VGSELECT_MAX_UPLOAD_MB per concurrent scan in the temp directory.
BrowserAny current browser; the UI is plain HTML/CSS/JS.

4. Installation

4.1 Bare metal or virtual machine

git clone https://github.com/rgvvvg5mpz-collab/VGSelect3A.git vgselect && cd vgselect
python3 -m venv .venv && source .venv/bin/activate
pip install --upgrade pip
pip install -e '.[service]'               # add ',llm' to enable the Claude-powered describe endpoint

export VGSELECT_SCAN_ROOTS=/srv/repos      # optional: directories that may be scanned by server path
export VGSELECT_CATALOG=/etc/vgselect/catalog.json   # optional: your model catalog (section 6)
vgselect-service                           # listens on 0.0.0.0:8080

4.2 Docker

Released images are published by CI to GitHub Container Registry on every tagged release; pull one instead of building:

docker pull ghcr.io/rgvvvg5mpz-collab/vgselect3a:0.4.0     # or :0.4 for the latest patch, :main for the latest build
docker run -d --name vgselect -p 8080:8080 \
  -v /srv/repos:/scan:ro \
  -v /etc/vgselect/catalog.json:/catalog.json:ro \
  -e VGSELECT_SCAN_ROOTS=/scan \
  -e VGSELECT_CATALOG=/catalog.json \
  --restart unless-stopped \
  ghcr.io/rgvvvg5mpz-collab/vgselect3a:0.4.0

To build locally instead:

docker build -t vgselect-3a:0.4.0 .
docker run -d --name vgselect -p 8080:8080 \
  -v /srv/repos:/scan:ro \
  -v /etc/vgselect/catalog.json:/catalog.json:ro \
  -e VGSELECT_SCAN_ROOTS=/scan \
  -e VGSELECT_CATALOG=/catalog.json \
  -e VGSELECT_ALLOW_GIT_CLONE=0 \
  --restart unless-stopped \
  vgselect-3a:0.4.0

The image runs as a non-root user, exposes 8080, and has a HEALTHCHECK on /health. To add the describe endpoint, uncomment the [service,llm] line in the Dockerfile and pass ANTHROPIC_API_KEY as a secret, never as a build argument.

5. Configuration reference

Everything is configured through environment variables. None is required for a first run.

VariableDefaultMeaning
VGSELECT_HOST0.0.0.0Bind address used by vgselect-service. Bind to 127.0.0.1 when a local reverse proxy fronts the service.
VGSELECT_PORT8080Listen port used by vgselect-service.
VGSELECT_SCAN_ROOTSempty (disabled)Colon-separated directories that POST /api/v1/scan {"path": ...} may read. Paths are resolved (symlinks followed) and must be inside a root; anything else returns 403. Leave empty to allow only zip uploads.
VGSELECT_ALLOW_GIT_CLONE0Set to 1 to allow POST /api/v1/scan {"git_url": ...}: a shallow clone into a temporary directory with a 5-minute timeout, deleted afterwards. Only https://, ssh:// and git@ URLs are accepted. Requires git and outbound access.
VGSELECT_MAX_UPLOAD_MB50Maximum size of a zip accepted by /api/v1/scan/upload. Larger uploads return 413.
VGSELECT_CATALOGbundled defaultPath to the model ecosystem catalog JSON (section 6). Read once at start-up.
VGSELECT_CORS_ORIGINSemptyComma-separated origins allowed to call the API from a browser on another host. Leave empty when the UI is served from the same origin.
ANTHROPIC_API_KEYunsetEnables /api/v1/describe when the llm extra is installed (section 7).
VGSELECT_DESCRIBE_ENABLEDunsetSet to 1 to enable describe when Anthropic credentials come from an ant auth login profile instead of an API key.

GET /health echoes the effective scan roots, catalog name and model count, and whether git cloning, describe and PDF generation are enabled, so you can verify configuration after every deploy.

6. Managing the available models

The set of models a role can be staffed with is data, not code: a JSON catalog. Changing which models are available, their prices, limits, approval or data clearance never requires a code change or a new image.

Where the catalog lives

SituationLocation
Nothing configuredThe bundled default inside the package: src/vgselect3a/catalogs/default.json. It has verified entries for the current Anthropic models and placeholder entries ("illustrative": true) for OpenAI, Google, self-hosted open-weights and Mistral models. Placeholders are never selected until you replace their numbers and mark them verified.
Production (recommended)Your own file, kept in version control next to your model registry, and passed with VGSELECT_CATALOG=/path/catalog.json (Docker: mount it read-only; Kubernetes: a ConfigMap).
Per request (experiments)Callers can send extra or overriding entries in catalog_models on any recommend, scan, PDF, skeleton or report-card request. These are merged over the server catalog for that request only and are never stored.
The catalog is read once at process start. After editing the file, restart the service (rolling restart in Kubernetes). GET /health reports the active catalog name and model count, and GET /api/v1/catalog returns the full active catalog, so you can confirm the new version is live.

How to add, change or retire a model

  1. Start from the bundled file if you do not have one yet: python -c "import importlib.resources as r; print(r.files('vgselect3a')/'catalogs'/'default.json')" prints its path; copy it and edit the copy.
  2. Add or edit an entry. One object per model; the full schema is in Model catalog. The fields that decide selection:
    • approved: false keeps the model in the catalog but rejects it for every role (the report shows "not approved by the platform team"). Use this to stage a model before clearance.
    • data_classes: which of public, internal, confidential, restricted the model may see. A role is only staffed by models cleared for the request's data_sensitivity.
    • platforms and regions: where the model is reachable and served; request policies filter on both.
    • reasoning_tier (1-5), tool_use (0-3), structured_output, strict_schema, context_window, max_output, modalities, thinking, effort_control: capability facts used as hard filters and floors.
    • ttft_s, tokens_per_s, input_price, output_price: latency and cost per role and per request. Take them from vendor price lists and your gateway telemetry.
    • evidence: measured accuracy per task family from your evals; the strongest signal the selector has and the only thing that can lift a lower-tier model into a role.
    • langchain_provider: the provider key the generated skeleton passes to init_chat_model (defaulted from provider; set it for self-hosted OpenAI-compatible endpoints, Bedrock, Vertex, Azure).
    • illustrative: set to false and fill verified_on once the numbers are real; otherwise the entry stays excluded by the default policy.
    • deprecation_date: set it when a vendor announces retirement; the selector penalises the model six months ahead and rejects it after the date.
  3. Retire a model by setting approved: false (keeps history and rejection reasons visible) or by removing the entry.
  4. Validate before deploying: vgselect catalog --catalog catalog.json lists the entries and fails on schema errors or duplicate ids; or POST /api/v1/catalog/validate with the list of entries against a running instance.
  5. Deploy and restart, then confirm with GET /health and run one recommendation to see the new model appear in "Model selection per role" (or in a role's rejected list with the reason).

Worked example: registering a self-hosted model cleared for restricted data

{
  "id": "acme-llama-70b", "display_name": "ACME Llama 70B (on-prem)", "provider": "self_hosted", "family": "llama",
  "platforms": ["self_hosted"], "regions": ["on_prem"],
  "approved": true, "data_classes": ["public", "internal", "confidential", "restricted"], "retention": "zero",
  "reasoning_tier": 4, "tool_use": 2, "structured_output": true, "strict_schema": false,
  "context_window": 128000, "max_output": 16000, "modalities": ["text"],
  "thinking": false, "effort_control": false,
  "ttft_s": 0.7, "tokens_per_s": 65, "rpm": 600, "max_concurrency": 32, "batch": false,
  "input_price": 0.25, "output_price": 0.75,
  "evidence": {"extraction": 0.91, "classification": 0.95},
  "langchain_provider": "openai", "illustrative": false, "verified_on": "2026-09-07",

Restricted-data workloads will now be staffed by this model where its tier and evidence satisfy the role, and the generated skeleton will list langchain-openai and an OPENAI_BASE_URL line for it.

Operational checklist for the catalog

  • One catalog per environment; review changes like code (approval, data clearance and regions are governance decisions).
  • Refresh prices and serving figures on a schedule; record verified_on.
  • Feed evidence from your eval pipeline whenever a task family is re-measured.
  • Never rely on placeholder numbers: keep illustrative: true until verified, and keep the default policy (require_verified) on in production.

7. Optional: the Claude-powered describe endpoint

POST /api/v1/describe and the UI's Describe tab send a prose description of the application to Claude and receive a filled-in profile; the recommendation itself stays deterministic. It is off unless all of the following hold:

  1. The llm extra is installed (pip install -e '.[service,llm]', or the commented line in the Dockerfile).
  2. Credentials are available: ANTHROPIC_API_KEY, or an ant auth login profile plus VGSELECT_DESCRIBE_ENABLED=1.
  3. Outbound HTTPS to api.anthropic.com is allowed from the service.

What leaves the network: the prose description only, never code, traces or catalog data. The call uses claude-opus-5 by default with refusal fallbacks enabled; the model can be overridden per request. GET /health shows describe_enabled. If you do not want any outbound calls, simply do not install the extra; the UI tab then reports the feature as unavailable.

8. Security model

The service ships without authentication. Deploy it behind your API gateway, SSO proxy, or service mesh (section 9). Anyone who can reach the port can scan whatever the allow-list permits and, if git cloning is enabled, make the host clone arbitrary repositories.
  • Path scanning is deny-by-default. It only works for directories under VGSELECT_SCAN_ROOTS; the check resolves symlinks and rejects traversal. Mount scan roots read-only.
  • Uploads are size-limited, extracted with a zip-slip check into a private temporary directory, and deleted after the request. They are never executed; the scanner only runs regular expressions over them.
  • Git cloning is off by default; when on, it is a shallow clone with a timeout. Do not enable it on hosts holding credentials you would not want used for cloning; prefer zip uploads or mounted read-only checkouts.
  • Traces may contain prompts or tool arguments from production. The report card only needs step types, agent names, token counts, latencies, tool names and an argument hash; strip payloads before upload (the native format has no field for them). Traces are parsed in memory and never stored.
  • Data leaving the host: nothing, unless describe is enabled (prose only) or git cloning is enabled (clone traffic to your remotes).
  • Responses contain file paths, line numbers and 160-character code snippets as scan evidence, the profile, the recommendation and (when supplied) the scan summary. Treat them with the same classification as the scanned code.
  • Secrets: the service reads no secrets except the optional Anthropic credential; pass it through your secret manager, not the image.
  • Process hardening: the image runs as a non-root user; the systemd unit above sets NoNewPrivileges and PrivateTmp; run with a read-only root filesystem and a writable /tmp if your platform supports it.
  • Dependencies: pin the image tag and rebuild on a schedule to pick up security fixes for FastAPI, Uvicorn, Pydantic and reportlab.

9. Reverse proxy, TLS and authentication

Terminate TLS and enforce authentication at the proxy. The UI and API are same-origin, so no CORS configuration is needed in the common case.

nginx

server {
  listen 443 ssl;
  server_name vgselect.internal.example.com;
  ssl_certificate     /etc/ssl/vgselect.crt;
  ssl_certificate_key /etc/ssl/vgselect.key;

  client_max_body_size 60m;          # >= VGSELECT_MAX_UPLOAD_MB plus traces
  proxy_read_timeout   120s;         # 300s if git cloning is enabled

  # authentication: e.g. auth_request to your SSO proxy, or an allow-list
  # include /etc/nginx/snippets/sso.conf;

  location / {
    proxy_pass         http://127.0.0.1:8080;
    proxy_set_header   Host $host;
    proxy_set_header   X-Forwarded-Proto https;
    proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
  }
}

Authentication options

  • SSO proxy (oauth2-proxy, Pomerium, your identity provider's gateway) in front of the whole site: simplest for the UI and the API alike; users authenticate once in the browser, CI uses a service token.
  • API gateway with per-key quotas for the API paths and SSO for the UI.
  • Network-only (VPN or private subnet) for a small team; still prefer SSO if the service can reach production repositories.

Set VGSELECT_CORS_ORIGINS only if a separately hosted front end calls the API.

10. Operations and monitoring

  • Stateless: scale horizontally; any replica can serve any request; no sticky sessions; rolling restarts are safe at any time.
  • Health: GET /health returns {"status":"ok", ...} with version, scan roots, catalog name and model count, and feature flags. Use it for readiness and liveness and for post-deploy configuration checks.
  • Logging: Uvicorn access and error logs go to stdout; ship them with your log agent. Use --log-level warning if access logs are noisy. Requests carry no user identity unless the proxy adds it; log at the proxy for audit.
  • Metrics: the service does not export Prometheus metrics itself; collect request rate, latency and error rate at the proxy or add an ASGI metrics middleware if you need them in-process. Track: request count by path, p95 latency for scan and PDF paths, 4xx/5xx rate, upload sizes.
  • Latency expectations: recommend: milliseconds; PDF: 0.1-0.5 s; skeleton: instant; scan: 0.1-10 s by repository size; report card: linear in trace steps.
  • Timeouts: proxy upstream timeout at least 60 s for scan endpoints (300 s with git cloning). Uvicorn needs no special timeout settings.
  • Temporary files: uploads and clones go to the system temp directory and are removed after each request; alert if the temp filesystem fills (a crash mid-request can leave a directory named vgselect-*; safe to delete).
  • Capacity: CPU-bound. Under sustained scanning of large monorepos, add replicas or a queue in front of the scan endpoints; interactive recommendations are negligible.
  • Backups: nothing to back up except your catalog file, which should already be in version control.
  • OpenAPI: the live document is at /openapi.json; a checked-in copy is in openapi/vgselect-3a.openapi.json (regenerate with python scripts/export_openapi.py). Publish it to your API catalog so clients can be generated.

13. Upgrades, rollbacks and tuning

  • Versioning: the version in pyproject.toml and src/vgselect3a/__init__.py is reported by /health, in every recommendation and in the PDF footer. Tag images with it.
  • Upgrade: build the new image, run pytest, deploy with a rolling restart, re-run the section-11 checks. No migrations exist.
  • Rollback: redeploy the previous image tag. The catalog file is forward and backward compatible as long as it validates.
  • Tuning estimates: latency and cost come from the catalog entries' serving figures and prices; for the bundled tiers also from MODEL_TIERS in src/vgselect3a/topologies.py and the constants at the top of src/vgselect3a/estimator.py. Replace them with measured figures and re-run the tests.
  • Tuning rules: rules live in src/vgselect3a/rules.py; each carries a citation key resolved in docs/industry_guidance.html. Add a rule and its evidence together.
  • Scanner patterns: the tables at the top of src/vgselect3a/scanner.py; extend them for in-house frameworks or tool conventions and add a fixture test.
  • Report card thresholds: src/vgselect3a/report_card.py holds the level rubrics, dimension weights and penalty sizes; Report card documents them.
  • Skeleton templates: src/vgselect3a/scaffold/langgraph.py, one function per topology; the suite syntax-checks every generated file.
  • PDF layout: src/vgselect3a/pdf_report.py; colours and header band are constants at the top.
  • User guide: edit docs/USER_GUIDE.html and run python scripts/sync_docs.py so the copy served at /guide matches; a test enforces this.

.claude/launch.json starts the service on port 8765 for the Claude Code browser preview from the project's .venv with the repository as the scan root. Create the venv with python3 -m venv .venv && .venv/bin/pip install -e '.[dev]'.

14. CI/CD

The repository's pipeline (.github/workflows/ci.yml)

  • test (every push and pull request): installs the dev extra, runs the test suite, checks that the committed OpenAPI export and the served user guide are current, builds a wheel and smoke-tests a clean install outside the source tree.
  • image (pushes to main and version tags): builds the Dockerfile and pushes ghcr.io/<owner>/vgselect3a tagged with the branch, the semver version, major.minor and the commit SHA, then starts the pushed image and checks /health and /guide.
  • release (version tags only): creates a GitHub release with notes taken from CHANGELOG.md and the image reference.

To ship a version: bump the version (section 13), update the changelog, merge to main, then tag and push the tag:

git tag -a v0.4.0 -m "VG Select: 3A 0.4.0" && git push origin v0.4.0

Mirror the image into your internal registry if production cannot pull from GHCR: docker pull ghcr.io/<owner>/vgselect3a:0.4.0 && docker tag ... registry.internal/vgselect3a:0.4.0 && docker push registry.internal/vgselect3a:0.4.0.

Using the service in other teams' pipelines

Teams can fail a pull request when an agent's implemented topology drifts from the agreed design, or when its report-card grade drops; see the Consumer guide. Give CI a service token at the proxy.

15. Go-live checklist

  1. Image built from a tagged commit; pytest green; OpenAPI export committed.
  2. Catalog file validated (vgselect catalog --catalog ...), placeholders marked illustrative or verified, approval and data classes reviewed by the platform team.
  3. VGSELECT_SCAN_ROOTS limited to read-only mounts; git cloning off unless required.
  4. TLS and authentication at the proxy; body size and timeouts set; CORS empty unless needed.
  5. Describe endpoint deliberately on or off; if on, credential from the secret manager and egress allowed only to api.anthropic.com.
  6. Readiness and liveness probes on /health; logs shipped; proxy metrics dashboards for rate, latency, errors.
  7. Section-11 smoke checks pass against the deployed URL, including /guide.
  8. User guide URL and the Claude Code skill (.claude/skills/vg-select-3a/, with VGSELECT_URL set) distributed to engineering teams.
After go-live, the two documents to keep current are this guide (configuration and operations) and the User guide served at /guide.
