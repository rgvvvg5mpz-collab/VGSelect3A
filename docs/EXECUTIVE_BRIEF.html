VG Select: 3A — Automated Agentic Architecture

Executive brief · What it is and why it helps the enterprise · September 2026

The problem

Every team building an AI agent faces the same early decision: one model call, one agent with tools, a fixed workflow, or a team of agents with an orchestrator. The choice sets latency, cost and reliability for the life of the product, and today it is made by instinct. The published evidence says instinct gets it wrong in both directions: multi-agent designs use about 15x the tokens of a chat interaction and fail 41-87% of the time in studied frameworks, mostly from coordination and specification errors; yet on breadth-first research the same designs cut wall-clock time by up to 90% and beat a single agent by 90%. Over-building wastes money and adds failure modes; under-building caps quality. Neither mistake is visible until production.

What VG Select: 3A is

A decision service that recommends the architecture of an agentic application before it is built, or audits one that exists. It scans the code repository to learn what the application actually does (tools, data sources, side effects, existing agent loops), combines that with the few facts only the team knows (latency budget, accuracy priority, cost sensitivity, volume), and ranks ten candidate architectures using rules drawn from Anthropic, OpenAI, Google, Microsoft, LangChain and peer-reviewed failure studies. Every rule carries its citation. The output is a ranked table with estimated latency and cost per option, the latency/accuracy frontier, a concrete decomposition plan (orchestrator, subagents, model per role, what runs in parallel) with a diagram, and the guardrails the evidence says every design needs. Each role is then staffed from the enterprise's own model catalog (Anthropic, OpenAI, Google, self-hosted and others) under governance policy: approval, data clearance, region, platform.

Delivered as
  • Web UI for design reviews (guided, tooltips throughout)
  • REST API with OpenAPI spec for CI and internal tooling
  • Claude Code skill so engineers get the answer inside their editor
  • CLI and Python library
  • Outputs: an architecture document (PDF) and a runnable LangGraph project skeleton
Answers it gives
  • Which topology, and why (cited)
  • What the current code implements and the gap
  • Fastest option that fits the budget; most accurate option and its cost
  • An architecture document (PDF) for the design review
  • A runnable LangGraph project skeleton for the chosen design

Why it helps the enterprise

  • Cost avoidance. Steers teams away from multi-agent designs when a single agent with a better model or prompt would score higher, and quantifies the token multiplier when multi-agent is justified. On a product doing 100k requests/day, choosing a 4x design over a 15x design where the evidence says they perform the same is the difference between tens and hundreds of thousands of dollars a month.
  • Faster, consistent design reviews. Architects and platform teams review a cited recommendation instead of debating from first principles. The same workload gets the same answer in every business unit.
  • Latency and accuracy made explicit. The trade-off is a table, not an opinion: product owners set the budget and the stakes; the service shows what each option costs in seconds and dollars.
  • Model governance enforced. Only approved models cleared for the request's data class and region can staff a role; every rejection is recorded, and roles no model can staff are surfaced before anything is built.
  • Governance built in. Every recommendation carries the guardrails the literature ties to failure: evaluation sets before structure, termination limits, verification at the orchestrator, gated approval for irreversible actions, tracing. Irreversible integrations (payments, email, ticketing) are detected from code.
  • Drift detection. Run in CI, it reports when an implementation's topology no longer matches the agreed design.
  • Auditable and self-hosted. Deterministic rules, no data leaves the network, evidence down to file and line, and a methodology document. Assumptions are printed with every result and can be recalibrated from the enterprise's own traces.

How to adopt

Week 1: deploy the container behind the internal gateway; publish the OpenAPI spec to the API catalog; distribute the Claude Code skill. Weeks 2-4: run it on the three to five agent initiatives in flight; require the 3A architecture PDF in each architecture review and start new implementations from the generated skeleton. Quarter: calibrate latency and cost assumptions from production traces; add in-house frameworks to the scanner and house conventions to the skeleton templates; track the metrics below.

Metrics to track
  • Cost per completed task before/after
  • p50/p95 latency vs budget
  • Share of agent projects with an eval set at design time
  • Architecture review cycle time
What it is not
  • Not a framework or vendor choice
  • Not a benchmark: estimates rank options, they do not predict production numbers
  • Not a substitute for evaluation: it tells you to build the eval first
