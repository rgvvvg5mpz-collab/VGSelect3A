VG Select: 3A — Agent Report Card

The report card grades an existing agent, or every agent in a multi-agent system, on what the code is (design complexity) and what it does at run time (behavioural complexity), against what the task needs (task complexity). It is produced by vgselect report-card, by POST /api/v1/report-card, by the UI when traces are added on the Scan tab, and it is embedded in the Markdown report and the architecture PDF whenever a scan or traces are supplied.

2. Design metrics (from the scan)

Tool count and overlapping tools; prompt definitions, prompt files and total prompt characters; loop patterns found (tool loops, routers, evaluator loops, fan-out, subagents, handoffs); delegation depth; and the presence of termination limits, memory, context management, structured output, prompt caching, approval gates, evals, tests, tracing, and irreversible side effects. They are listed in scan.design and drive the Governance dimension.

3. Behavioural metrics (from traces)

Per run and per agent: steps, LLM calls and tool calls (mean, p50, p95, CV), distinct tools, tool error rate, repeated identical tool calls (loop signal), runs ended by a limit, by error or timeout, handoffs and spawns per run, verification and human-approval rates, branching factor (distinct next actions per state), trajectory diversity and outcome consistency across repeated runs of the same task, tokens per run, peak context and context growth per step, latency p50/p95, cost per run, cost per completed task, and successes per thousand tokens.

Letter grades: A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 60, F below. The overall score is the weighted mean of the dimensions that could be measured; without traces only Governance and Complexity fit are graded and the card is marked design-time.

Per-agent cards (multi-agent systems): every agent name seen in the traces gets its own behaviour metrics, is matched to a plan role and its chosen model, and is graded on tool errors, loops, step variance, context growth and peak context.

5. Trace format

Native format is JSON Lines, one record per task run:

{"schema": "vgselect-trace/1", "task_id": "t-42", "run_id": "r-1", "success": true, "terminated_by": "end_turn",
 "latency_ms": 8400, "cost_usd": 0.031,
 "steps": [
   {"agent": "lead", "type": "llm", "input_tokens": 3100, "output_tokens": 220, "latency_ms": 1800},
   {"agent": "lead", "type": "spawn", "name": "worker_1"},
   {"agent": "worker_1", "type": "tool", "name": "search_kb", "args_hash": "a1", "latency_ms": 300, "error": false},
   {"agent": "worker_1", "type": "llm", "input_tokens": 4800, "output_tokens": 500, "latency_ms": 2600},
   {"agent": "lead", "type": "verify", "passed": true}
 ]}
  • type: llm, tool, spawn, handoff, verify, human, other.
  • agent: the role or agent that took the step; omit for single-agent systems.
  • task_id repeated across runs enables consistency and trajectory-diversity metrics; success enables quality grading; terminated_by (end_turn, limit, error, timeout, human) enables termination metrics.
  • args_hash: any stable hash of tool arguments, used to detect repeated identical calls.

Also accepted: a JSON array of such records; a LangSmith-style run export (nested child_runs with run_type llm/tool/chain); OpenTelemetry GenAI spans (gen_ai.operation.name, gen_ai.usage.*, gen_ai.tool.name, trace_id). Adapters are best effort: success and termination are unknown unless present. Fictional traces for demos: vgselect3a.traces.synthesize_traces.

6. Using it

vgselect report-card --scan . --traces runs.jsonl --set latency_budget_s=8 --set accuracy_priority=4
vgselect recommend  --scan . --traces runs.jsonl --format pdf --out architecture.pdf   # card inside the PDF
curl -s $VGSELECT_URL/api/v1/report-card -H 'content-type: application/json' -d '{"profile": {...}, "scan": {...}, "traces": [...]}'

In the UI, add a traces file on the Scan tab; the report card appears above the options comparison, with per-agent rows for multi-agent systems.

7. Reading it

Start with the mismatches: they are the actionable gap between what the task needs, what was built, and what the agent actually does. Then the weakest dimension. For multi-agent systems, the per-agent rows show which role loops, errors, or carries the token load. Grades are relative to your budget and stakes as stated in the profile, so set those honestly.
