VG Select: 3A — User Guide

For everyone who uses the deployed VG Select: 3A (Automated Agentic Architecture) web application: architects, engineers, product owners and reviewers. No installation needed; open the URL your platform team gave you. Engineers who want the API, CLI or Claude Code skill should also read the Consumer guide.

1. What it does

VG Select: 3A answers one question for an application built on LLM agents: what shape should it have? One model call, one agent with tools, a fixed workflow, or a team of agents with an orchestrator, and which model should run each part. It answers with evidence: every recommendation cites published industry guidance, shows the estimated latency and cost of each option against your budget, and hands you two things to take away: an architecture document (PDF) for your design review and a runnable project skeleton (LangGraph) for the chosen design.

If you already have an agent, it can also grade it: a report card from the code and, if you provide run-time traces, from how the agent actually behaves.

It is deterministic. The same inputs always produce the same answer, and every number comes with its assumptions. Nothing you enter is stored.

2. When to use it

  • Before building a new agentic application: to choose the topology and the models, and to produce the design document.
  • During a design review: to replace opinion with a cited, comparable analysis; reviewers can see why the runner-up lost.
  • When an agent misbehaves or costs too much: to see whether it is over-built, under-controlled, or simply on the wrong model, and what to change.
  • When a model catalog or governance rule changes: to check which roles are still staffable under the new policy.
The estimates rank options; they are order-of-magnitude, not measurements. The tool will tell you when no option fits your budget rather than pretend one does.

3. A five-minute tour

  1. Open the application. The left panel is the input side with three numbered steps; the right panel shows results.
  2. In Step 1, pick Example and choose a scenario, for example "Deep research". The form in Step 2 fills in.
  3. Press Recommend architecture in Step 3.
  4. Read the verdict card at the top of the results: the recommended architecture, whether it fits your latency budget, estimated cost and tokens, and the reasons with their sources.
  5. Scroll down: options compared, a latency-versus-fit chart, the model chosen for each role, the build plan with a diagram, and next steps.
  6. Press Architecture doc (PDF) to download the document, or LangGraph skeleton (.zip) to download the project.

Every field, table header and citation has an i button or dotted underline; hover or focus it for an explanation.

4.1 Scanning a repository

Three ways to point at the code:

  • Upload a zip. Zip the project folder and drop it on the field (or click to choose). Dependency and build directories (node_modules, .git, venv, dist) are skipped automatically, so you do not need to exclude them, though smaller uploads are faster. Limit: 50 MB by default.
  • Server path. If your platform team mounted repositories on the server, type the path. The status line lists the allowed roots.
  • Git URL. If cloning is enabled on your deployment, paste an https URL of a repository the server can reach.

Press Scan and pre-fill profile. The form fills in and the results show a "What the scan found" panel with each inferred field, a confidence percentage, the reason, and the evidence with file and line. Treat inferences under 50% as guesses and correct them in Step 2. The scan cannot see your latency budget, how costly errors are, cost sensitivity or volume; set those yourself.

The scanner only reads code and configuration; prose files and generated outputs are ignored. Nothing is executed.

4.2 Adding run-time traces

On the Scan tab, the "Run-time traces (optional)" field accepts a file of recorded runs. With it, the report card grades the agent's real behaviour (success, loops, latency, tokens, per-agent rows). See section 9 for the format and how to get one.

5. Step 2: Describe the workload

Twenty-six fields in six groups. Each has a default, an i explanation, and the eight that most change the answer are marked key. A sentence under the form restates what you are asking for as you edit; the counter shows how many fields differ from defaults.

About the application

FieldHow to set it
NameShort name; it appears in the PDF title and the download file names.
DescriptionOne or two sentences; printed on the PDF cover.

Task shape

FieldHow to set it
Task complexity keytrivial: a lookup or classification with one obvious step. simple: one-step generation. moderate: a few dependent steps. complex: many dependent steps needing judgment. open ended: the steps cannot be listed in advance; the system must explore.
Steps predictable keyYes if you could write the sequence of steps as a fixed script (workflow). No if the model has to decide what to do next at run time (agent). This is the single most important switch.
Scope breadthHow many distinct domains or skills one request can touch: a support bot covering billing, shipping and technical issues is 3.
Parallel subtasks keyIndependent pieces of work in one request that could run at the same time (research across four sources: 4). Use 0 or 1 when there is none.
Output typeshort answer, structured data (JSON for a system), long document, code change, or action (the deliverable is something done).

Tools

FieldHow to set it
Tool countDistinct functions the application can call. The scan counts them for you.
Tool calls per task keyTypical calls on one request. If unsure, look at a few real conversations and count. This drives latency more than anything else.
Tool dependencysequential if each call depends on the last; independent if they could be issued together; mixed otherwise. Independent calls make everything faster.
Tool side effectsread only; reversible writes (drafts, files under version control); irreversible (sending email, moving money, deleting, opening tickets). Irreversible tools add an approval gate to the plan.
Tool overlapYes when several tools do similar things (three different "search" tools). Overlap, more than count, is what confuses agents and argues for specialists.
Tool latency (seconds)Average time one tool call takes. Deterministic internal APIs are often 0.2-0.5 s; web search 1-3 s.

Knowledge and context

FieldHow to set it
Knowledge sourcesDistinct places the application must look things up: vector stores, wikis, databases, the web.
Retrieval depth keynone; single lookup (one query answers it; classic retrieval-augmented generation); multi hop (follow-up queries depend on earlier results); exhaustive (breadth-first coverage of a topic across many documents). Exhaustive is where subagents pay off.
Context tokens per taskRoughly how much text must be read to answer one request. A few pages: 5,000. A long report: 50,000. A whole corpus: hundreds of thousands. This decides whether one context window is enough.

Quality and risk

FieldHow to set it
Accuracy priority keySlider from "best effort is fine" (1) to "errors are very costly" (5): money, safety, compliance. High values make the tool tolerate more latency and add verification.
Single-agent baselineIf you have measured a plain single agent on your own evaluation set, enter its accuracy (0 to 1). Leave at -1 if not measured. Above about 0.45, adding agents tends to hurt, so this can change the answer.
Verifiabilitynone (subjective), partial (rubric or spot checks), strong (tests, schemas, ground truth). Strong verifiability enables evaluator loops and voting.
Error recoverabilityHow easily a wrong action can be caught and undone: easy (review before commit), moderate, hard (acts on the world immediately).

Operating constraints

FieldHow to set it
Latency budget (seconds) keyThe end-to-end time one request may take, at the median. Chat: 3-10 s. Background job: minutes. The budget is the line every option is measured against.
Interactionsingle turn; multi turn (conversational); long running (one task over many minutes or hours).
Requests per dayVolume. It weights cost and decides whether batch processing is worth mentioning.
Cost sensitivity keySlider from "cost is no concern" (1) to "cost dominates" (5). High values penalise designs that multiply tokens.
Human in loopYes if a person can approve risky actions during a request.
Data sensitivity keypublic, internal, confidential, restricted: the most sensitive data a request can contain. Only models cleared for that class in your organisation's catalog can be chosen.
If you only set five things, set: task complexity, steps predictable, tool calls per task, latency budget, and accuracy priority. Then data sensitivity, because it gates which models are allowed.

6. Model ecosystem

Below the form, the collapsible Model ecosystem group constrains which models from your organisation's catalog may staff each role:

  • Allowed providers, platforms and regions: tick to restrict; leave all unticked for no restriction. Typical uses: "EU only", "self-hosted only", "no provider X".
  • Allow illustrative entries: some catalog entries are placeholders with example numbers. They are excluded by default; tick only for what-if exploration and never rely on their figures.

The status line at the bottom of the input panel shows which catalog is loaded and how many models it contains. Ask your platform team to add or clear models; you cannot change the catalog from the UI.

7. Step 3: Read the results

Press Recommend architecture. Results appear on the right (or below on a narrow screen), top to bottom:

7.1 Verdict card

  • Recommended architecture and its family (single, workflow, multi-agent).
  • A budget badge: Fits the budget (estimate at or under 70% of your budget), Tight (70-100%), Exceeds (up to 2×) or Far over.
  • Four tiles: estimated median latency with a bar against your budget, cost per request at list prices, tokens as a multiple of one plain model call, and the score.
  • A one-paragraph headline, which also names the fastest option that fits when the winner does not, and the most accurate option when it differs.
  • Why this architecture: the rules that favoured it, each with a weight and a citation chip; hover the chip for the source. Counter-signals are collapsed underneath.

7.2 What the scan found (after a scan)

Frameworks, tool count, knowledge sources and side effects as chips; the topology implemented today; a table of inferred fields with confidence and reason; and an expandable evidence table with file and line. When the recommendation differs from what is implemented, a Current vs. recommended comparison shows score, latency, cost and tokens side by side.

7.3 Agent report card (after a scan or traces)

Explained in section 9.

7.4 Compare the options

All ten architectures ranked. Columns: Score (fit plus latency and cost adjustments), Fit (the evidence-based rules alone), Latency, Budget verdict, Cost, Tokens, Calls. Struck-through rows cannot do the job at all (for example a single call cannot make tool calls). Press Why on any row to see every rule that fired for it and the estimate's assumptions.

Under the table, the latency versus structural fit chart: each dot is a viable option; higher is a better evidence fit, further left is faster; the dashed line is your budget; the highlighted dot is the recommendation; blue dots are on the frontier, meaning no option is both faster and a better fit.

7.5 Model selection per role

One row per role in the plan: what the role needs (minimum capability tier, its share of the latency budget, context to hold, tools, structured output), the chosen model and effort setting, a fallback on another provider where possible, this role's own estimated latency and cost per call, and scored alternatives. Press Why for the rationale and the list of rejected models with reasons. Roles no model can staff are marked unfilled; the reasons (not approved, not cleared for the data class, region, capability) tell you what to ask the platform team for.

7.6 Build plan

Cards for each component (orchestrator, workers, router, evaluator, code steps) with the model, effort, tools and whether it runs in parallel; a diagram; briefing rules for subagents when the design has them; and the Mermaid source for wikis.

7.7 Next steps

A checklist of cross-cutting recommendations the evidence ties to success regardless of topology: build a small evaluation set first, set termination limits on every loop, verify at the orchestrator, gate irreversible actions, cache prompts, stream, manage context. Each has a citation. Tick them off in your review.

7.8 Assumptions behind the numbers

The serving assumptions, reading load and output size the estimates used. If they do not match your environment, the numbers will not either; tell your platform team, who can update the catalog.

9. Grading an agent you already run

Choose Grade agent in Step 1. Drop the traces file, optionally the repository zip, set at least the latency budget and accuracy priority in Step 2 (they set the bar the grades are measured against), and press Grade agent. The results open on the report card. Alternatively, scanning the repository from the Scan tab (section 4.1) without traces gives a design-time report card: design complexity from the code (tools and overlap, delegation, handoffs, loops, prompt load), governance checks (evaluation harness, approval gates, termination limits, tracing, structured output), and mismatch flags against the task complexity you described.

Add a traces file and the card becomes a full report card with behaviour graded from real runs:

  • Three complexity tiles: task (what you described), design (what the code is), behaviour (what the agent does). Big gaps between them are the story: over-built, under-built, or improvising structure at run time.
  • Six graded dimensions with letter grades and findings: outcome quality, reliability and control, cost and token efficiency, latency, governance and guardrails, complexity fit. An overall grade weights them.
  • Mismatches with severity and a concrete action, for example "Loops without limits: repetition in 31% of runs, 9% hit a limit, and no termination limits are in code. Action: add max turns and explicit stop criteria; cache identical tool calls."
  • Behavioural metrics (expandable): success and consistency across repeated runs, steps per run and their spread, tool calls and errors, repeated identical calls, runs ended by a limit, branching factor, tokens, peak context, latency, cost per completed task.
  • Per-agent cards for multi-agent systems: every agent seen in the traces gets its own row and grade, matched to its role and model, so you can see which agent loops, errors or carries the token load.

Getting a traces file

Ask the engineers who run the agent to export runs in one of three shapes: the native JSON Lines format (one record per run with typed steps, agent name, token counts, latency, success and how the run ended), a LangSmith run export, or OpenTelemetry GenAI spans. The Report card reference has the exact format. Only counts, names, timings and a hash of tool arguments are needed; no prompts or customer data should be in the file. A few dozen runs, ideally with each task run twice, give meaningful consistency figures.

Grades are relative to the budget and stakes you entered in Step 2. Set those honestly before judging the grade.

10. Worked examples

These mirror the case studies shipped with the tool.

10.1 Call summarisation (batch, structured output)

A contact centre summarises 50,000 calls a day into the CRM within a minute. Scan shows a single model call posting to Salesforce; you set complexity moderate, steps predictable, structured data, accuracy 4, budget 60 s, cost sensitivity 4, data confidential, a measured baseline of 0.78. Result: a prompt chain (extract, validate in code, finalise) at about 26 s, on a mid-tier model for both stages. The gap table shows the current single call scores lower because predictable steps with gates beat one big prompt. The report card grades the pipeline well, with a note that the eval harness exists but tests should cover compliance flags.

10.2 Robo-advisor (multi-domain conversation)

A chat adviser across planning, tax, risk and products with ten tools and three knowledge bases, budget 15 s, accuracy 5, data confidential, baseline 0.61. Scan detects an evaluator loop and overlapping search tools. Result: a router to four domain specialists, each with its own small tool set, on a small model for the router and a cleared mid-tier model for the specialists, with a fallback on another provider. The tool is honest that even this exceeds the 15 s budget and points at the tool rounds. With traces, the report card is an F: 48% success, loops without limits, p95 three times the budget, and the single "agent" row flagged while the evaluator row is stable. The mismatches list says what to fix first.

10.3 Account balances assistant (restricted data)

An in-app assistant answering balance and cost-basis questions from deterministic APIs, budget 5 s, accuracy 5, cost sensitivity 5, data restricted, baseline 0.88. Result: keep the single agent; the ranking is estimated on the only model cleared for restricted data (an on-premises model), and the cloud models appear in the rejected list with "not cleared for restricted data". The headline says the topology already matches and to focus on the next steps (caching, streaming) because the budget is tight.

11. Using it in a design review

  1. Scan the repository (or load the closest example) and agree the five key fields with the product owner: complexity, predictability, tool calls, budget, stakes. Add data sensitivity.
  2. Download the PDF and circulate it before the meeting.
  3. In the meeting, walk the verdict card, then the Compare the options table: ask what would have to be true for the runner-up to win (usually a different budget or stakes) and try it live by changing the field.
  4. Go through Model selection per role: confirm the platform team agrees with the data class and any unfilled roles.
  5. Turn the Next steps checklist into tickets; the first one is always the evaluation set.
  6. Record the decision with the profile JSON so future scans can be compared against it.

12. What leaves your browser

  • Profile values, policy choices, uploaded zips and traces go to your organisation's VG Select server, are processed in memory or a temporary directory, and are deleted when the request finishes. Nothing is stored.
  • Nothing goes to any third party, with one exception: the Describe tab sends your prose description (only that) to the Claude API, and only if your deployment enabled it.
  • Scan results include file paths and short code snippets as evidence; treat downloaded reports with the same classification as the code.

13. Glossary

TermMeaning
Topology / architectureThe shape of the system: how many model calls or agents, and how they are connected.
Single callOne prompt, one response; retrieval done in code beforehand.
Single agentOne model in a loop deciding which tools to call until the task is done.
Prompt chainFixed sequence of model steps defined in code with checks between them.
RouterA cheap classification step sends each request to one specialist.
Parallel sectioningCode splits the task into independent parts run at the same time, then merges.
Parallel votingThe same task run several times; answers are voted or judged.
Evaluator-optimizerA generator and a separate evaluator loop until the output is accepted.
Orchestrator + workersA lead agent plans, briefs subagents that run in parallel, then verifies and synthesises.
HierarchicalTwo levels of delegation: orchestrator, domain leads, workers.
HandoffsSpecialists pass the conversation to one another; no central manager.
FitThe sum of evidence-based rules that favour or disfavour an option, before latency and cost.
ScoreFit plus a latency adjustment against your budget and a cost adjustment weighted by your cost sensitivity.
FrontierThe options for which no other option is both faster and a better fit.
TierA model's capability level, 1 (trivial) to 5 (frontier), from the catalog.
EffortHow much reasoning a model is asked to spend on a role (low to max) when the model supports it.
FallbackA second model for a role, preferably on another provider, used on outages or refusals.
Data classpublic, internal, confidential, restricted; models are cleared per class.
TracesRecorded runs of an agent: steps, tools, tokens, timings, outcome.
Report cardGrades for an existing agent from its code (design) and traces (behaviour).

14. FAQ

  • Everything says it exceeds my budget. The tool is telling you the budget is incompatible with the tool calls and reading per request. Reduce tool calls, make them independent, shorten outputs, or relax the budget, and watch the table update.
  • I expected multi-agent and got a single agent. Multi-agent only scores with independent sub-tasks, breadth-first research, or reading that overflows one context window; and above a measured baseline of about 45% it is penalised. Check parallel subtasks, retrieval depth and context tokens.
  • A role is unfilled. No model in your catalog passed the filters for it, usually the data class or approval. The "Why" expander lists each rejection; forward it to the platform team.
  • Can I change the models offered? Not from the UI. The catalog is managed by the platform team.
  • Why are the cost numbers different from my bill? They are list-price estimates without caching, meant for ranking. Your report card, from traces, shows measured cost per completed task.
  • Is my code stored? No. See section 12.
  • Where do the rules come from? Published guidance from Anthropic, OpenAI, Google, Microsoft, LangChain and peer-reviewed failure studies; every citation chip names its source, and the full evidence is in the Industry guidance document shipped with the tool.
  • Can I use this without the UI? Yes: the same engine is available as an API, a command-line tool and a Claude Code skill; see the Consumer guide.
